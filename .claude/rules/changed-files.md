## В конце хода - список изменённых файлов

Под ответом каждого хода, который что-то менял, стоит строка со списком файлов: путь от корня проекта,
добавленные строки зелёным, удалённые красным. У созданного файла только плюс. Клик по строке открывает
файл в редакторе по полному пути из вызова. Заголовка и слов нет: под списком стоит «Worked». Просили из
Android Studio («изменённые файлы перечисляются, а клик их копирует») - то есть хотели не ссылки в тексте
ответа (они и так открывались), а список, который не зависит от того, что модель решила написать.

- **Цифры берутся у CLI, а не у вызова** (`changeOf` в `feed/changes.ts`). На каждую правку CLI отвечает
  структурной половиной результата: `structuredPatch` с применённым диффом, а Write ещё и `type: 'create'`
  или `'update'`. Живой поток несёт её как `tool_use_result`, транскрипт - как `toolUseResult` (проверено на
  2.1.293 для Edit и обоих видов Write). Из вызова этого не узнать: `replace_all` меняет текст столько раз,
  сколько он встречается, а Write поверх файла удаляет строки, которых вызов не называет.
- **Строки созданного файла считаются по аргументу вызова** (`input.content`), а не по `content` результата.
  `JournalTrim` режет длинные строки внутри результата и бережёт аргументы вызова, так что в истории и на
  телефоне файл длиннее 8 КБ иначе посчитался бы по обрезку. Строки патча короткие, их обрезка не трогает.
- **Если структурной половины нет** (старый CLI, кадр телефона обрезан), считается по вызову: Edit - так же,
  как дифф на карточке, Write - по `content` и фразе «File created successfully». Для субагента без неё не
  гадается ничего.
- **Субагенты входят в список** (`noteChanges`). Их вызовы не становятся карточками ленты, это строки лога,
  поэтому список копится по ходу результатов в `PanelState.turnChanges`, а не собирается из ленты в конце:
  результат с диффом - единственный момент, когда правку субагента вообще можно посчитать. В истории их нет:
  у субагента свой файл транскрипта, и реплей его не читает.
- **Ход закрывается в разных местах, и каждое кладёт список** (`closeChanges`): `result` (перед «Worked»),
  тихая остановка, смерть процесса (перед строкой падения), подмена процесса, новое сообщение человека
  (страховка на случай хода без результата) и `/clear` (там список просто сбрасывается). В реплее событий
  `result` нет вовсе, поэтому ход закрывает следующее сообщение человека (`addReplayedPrompt`) и конец
  реплея (`applyReplayFinished`, через него же идёт страница истории).
- **Файл, тронутый дважды за ход, - одна строка с суммой** (`withChange`). Созданный и потом поправленный
  остаётся созданным, и его плюс - это сколько в нём строк вышло: добавленное минус удалённое правками.
  Правка, которая ничего не изменила (Write того же текста), строки не даёт.
- **Структурная половина доверяется, только когда в событии один результат** - CLI так и шлёт, по сообщению
  на результат. Пачка из нескольких считается по вызовам: половина принадлежит событию, а не блоку.
- **Путь в строке - от корня проекта, файл вне проекта - целиком** (`projectRelative` в `feed/changes.ts`, с
  тестом; `projectRoot` в `App.tsx` из `init` IDE, проп `Feed` → `ChangesRow`). Считается при отрисовке по
  корню, который назвала IDE, а не при записи по рабочей папке агента: вкладка узнаёт папку агента только из
  его `system/init`, и в песочнице список вышел из полных путей (`…ments/Projects/…/sandbox-project/src/…`).
  Разделители сравниваются как один, буква диска без регистра (IDE пишет `/`, CLI на Windows `\`). Телефону
  путь проекта не отдаётся вовсе, поэтому там остаётся `FileChange.shown` - от папки агента, если она
  известна. Вопрос перед «Revert all» файлы не перечисляет: список стоит прямо за ним.
- **Длинный путь теряет папки с начала, а не имя** (`.changeFolder` с `direction: rtl`, внутри `ltr`):
  `…n/java/com/example/home/HomeScreen.kt`. Ближняя к файлу папка говорит больше корня.
- **Цифры на заголовке карточки правки считаются по тому же диффу, что под ней** (`metaFor` в `feed/tools.ts`).
  Раньше заголовок считал старый и новый текст целиком и писал «+2 −1» над диффом из одной добавленной строки,
  а рядом со списком хода это читалось как два разных ответа.
- **На телефоне строки только читаются**: редактора нет (`useOpenFile` там null).
- Проверить без IDE: харнесс, сценарий «The files a turn changed» - четыре файла с созданным, потом ход, где
  созданный файл правится и его цифры складываются. Клик печатает в консоль полный путь. Живьём: в песочнице
  попросить агента создать файл и поправить другой - список встаёт под ответом, клик открывает файл.

## Откат файла и всего хода

У каждой строки списка кнопка отката, у списка - «Revert all» (если откатывать есть что больше чем в одном
файле). Попросил Макс сразу после появления списка: раз видно, что ход поменял, логично это и вернуть.

- **Откатывается дифф хода, а не копия файла** (`ChangeRevert.undo` в IDE, с тестом). Панель шлёт ханки,
  которые CLI применил (`FileChange.edits`), IDE применяет их в обратную сторону к файлу, каким он стоит
  сейчас: последняя правка первой, в правке - последний ханк первым, ханк ищется там, где он был, и дальше
  вширь (выше могли добавиться строки). Поэтому чужие правки в других местах файла - следующий ход, рука в
  редакторе - остаются. Если строк хода в файле уже нет как он их написал, ответ «changed since», и файл не
  трогается: записанная назад копия молча стёрла бы всё, что сделали после.
- **Созданный файл удаляется, только если в нём всё ещё ровно то, что оставил ход** (созданный и поправленный
  в том же ходе - тоже: правки снимаются первыми, остаток сравнивается с `create`). Содержимое для сравнения -
  из аргумента вызова, не из результата: результат режет `JournalTrim`.
- **Конец строки файла возвращается тоже**: пометка `\ No newline at end of file` после строки `-` или ` `
  говорит, что старый файл кончался без перевода строки, и ханк, дошедший до конца файла, восстанавливает это.
- **Пишется через документ IDE командой** (`FileReverts`, имя «Revert Claude's Changes»), а не на диск: редактор
  с этим файлом меняется на месте, заменяется только отличающийся кусок (каретка и складки остаются), а откат
  отката - обычный Cmd+Z в этом редакторе. Удалённый файл остаётся в Local History. До отката сохраняются
  несохранённые буферы (`UnsavedEdits.flush`), а файл перечитывается с диска синхронно - агент писал его снаружи.
- **Строка без диффа кнопки не получает.** Если хоть одна правка файла пришла без структурной половины,
  точно откатить нечего, и угадывать по вызову нельзя (`withChange` сбрасывает `edits` целиком).
- **Итог - всем и в журнал** (`changesReverted`, `ClaudeSessionHub.revertChanges` → `broadcast`). Второе окно,
  перезагруженная панель и телефон видят те же строки откаченными; отказ - факт о файле, а не об экране,
  который нажал. Список ищется по имени из первого вызова хода (`changes-<tool_use_id>`), а не по счётчику
  ленты: лента, пересобранная из журнала с отпущенной головой, считала бы иначе и пометила бы чужой список.
- **Уже откаченный файл отвечает «reverted», уже возвращённый - «restored», без записи** (`ChangeRevert.revert` и
  `bringBack`, с тестами). Отметки откатов живут в журнале хаба, а перезапущенная IDE поднимает вкладку из
  транскрипта, где их нет: строка снова предлагала откат, и ответ «changed since» про файл, который стоял ровно
  там, куда его поставил человек, читался как «не срабатывает» (поймано в песочнице). Поэтому если строк хода в
  файле нет, а на их месте строки, которые ход заменил, откат засчитывается без записи, и строка сразу
  предлагает вернуть; так же наоборот. Созданный файл, который ещё на месте, откаченным не считается никогда.
- **Проверка «уже откачен» держит ханк у края файла** (`anchored` в `ChangeRevert.apply`, тест «a line appended
  and then rewritten by hand»). У ханка с неполным контекстом (меньше трёх строк) он касается начала или конца
  файла, и в проверке обязан касаться их и сейчас. Поймано на финальной проверке: агент дописал строку в конец
  README, её поправили руками, и откат ответил «Reverted» - три строки контекста перед ней были на месте, только
  уже не последними. Настоящий откат и возврат не привязаны: строку, добавленную кем-то под строкой агента,
  откат оставляет.
- **У карточки правки цифры из того же диффа** (`withHeadCounts` в `noteChanges`): `replace_all` в вызове называет
  одну строку, и над «+8000 −8000» в списке карточка писала «+1 −1».
- **Нажатие ждёт ответа по счётчику, а не по надписи** (`FileChange.answers`, растёт в `applyChangesReverted` на
  каждый ответ о файле; `pressed` в `ChangesRow` помнит счётчик в момент нажатия). Сначала ждали, пока строка
  скажет что-то другое, и повторное нажатие после отказа висело на «Reverting…» навсегда: IDE отвечала тем же
  «changed», надпись не менялась, ответ не засчитывался. Поймано в песочнице. Страховка сверху - 15 секунд
  (`PRESS_PATIENCE_MS`): нажатие без ответа (окно закрыли, сообщение потерялось) забывается, и строку можно
  нажать снова. Живьём ответ приходит за доли секунды.
- **Ничего не спрашивает, «Revert all» тоже.** Сначала «Revert all» поднимал вопрос (`Confirm` в `App`), и его
  сняли по прямой просьбе: у каждого отката есть возврат той же строкой («Bring all back» для всего списка), так
  что вопрос защищал от того, что и так отменяется одним нажатием.
- **Список не меняет высоту, пока IDE отвечает.** Нижняя строка с «Revert all» / «Bring all back» стоит всегда,
  когда файлов с диффом больше одного, а кнопки в ней на время ожидания только гаснут (счёт ведётся вместе с
  ждущими строками, `min-height` у `.changesFoot`). Раньше на время ответа «Revert all» пропадала вместе со
  строкой, а через долю секунды появлялась «Bring all back» - список прыгал на строку (жалоба из песочницы).
  Подпись у файла - в одну строку с обрезкой, иначе в узкой панели она переносилась и растила строку.
  «Reverting…» / «Bringing back…» пишется, только если ответа нет дольше полусекунды (`QUIET_PRESS_MS`):
  IDE отвечает за доли секунды, и мелькание подписи по всем строкам было рывком ни о чём. Замер в харнессе:
  118 пикселей на всём пути отката и возврата, на 1280 и на 360.
- **Откаченное возвращается той же кнопкой, повёрнутой вперёд** (`restore` у `revertChanges`, `ChangeRevert.redo`).
  Попросил Макс сразу после отката. Это тот же дифф, приложенный вперёд: ханк ищется по старой стороне от
  `oldStart` (панель шлёт его рядом с `newStart`; IDE без него берёт `newStart`), и если строк, которые ход
  заменил, на месте нет, ответ «changed», а файл не трогается. Удалённый созданный файл пишется заново вместе с
  папками, а файл, стоящий на его месте, чужой, если в нём не ровно то, что оставил ход. У списка «Bring all
  back», когда откачено больше одного файла.
  Отказ возврата оставляет строку откаченной и пишет причину рядом (`FileChange.restoreRefused`), а не
  выдаёт её за отказ отката. Отметка нажатия забывается, как только пришёл ответ (см. ниже про счётчик): иначе
  «Revert all» после возврата снова показывал над строкой «Bringing back…» от старого нажатия.
- **Телефону откат запрещён** (`revertChanges` в `RemoteCommands.DENIED`): откат решают, глядя на файл, а файл на
  столе. Строки там только показывают, чем кончился откат за столом. Счёт фичи - `revert_changes`
  (`UsageFeatures`, подпись в usage-service).
- Агент об откате узнаёт сам: CLI замечает, что прочитанный им файл изменился снаружи, и говорит модели об
  этом на следующем шаге.
- Проверить без IDE: харнесс, тот же сценарий - плеер отвечает на откат «reverted», а манифесту - «changed»,
  так видны оба вида строк; возврат плеер всегда принимает. Живьём: попросить агента поправить
  файл и создать новый, откатить правку (файл как был), созданный (удалён), а у третьего перед откатом руками
  поменять написанную агентом строку - откат обязан отказать и не тронуть файл.

## Файл, который ход менял не только правками

Пришло отзывом Макса 2026-10-15 со скриншотом: из пяти файлов хода откатился только последний, у четырёх
созданных «Changed since, left as is», хотя их после хода никто не трогал. Разобрано по транскрипту: файл
менялся не одними Write и Edit, а дифф хода знал только их. Три дороги, все обычные:

- **Форматтер после каждой правки** (хук PostToolUse в настройках проекта). CLI так и пишет агенту: «PostToolUse
  hook modified ... after your edit (likely a formatter)». Записанные 945 строк CSS стали 2800 сразу после Write,
  а следующий Edit пришёл уже в координатах отформатированного файла.
- **Скрипты и `sed` самого агента в том же ходе** (python-патчи, `cat >>`). Вызов Bash не отчитывается диффом.
- **CLI сам дописывает файл памяти**: в frontmatter появляются `node_type`, `originSessionId`, `modified`, а
  описание берётся в кавычки. `content` результата это уже знает, аргумент вызова - нет, а панель держит созданный
  файл именно по аргументу (см. выше про `JournalTrim`).

Решение - **сверка хода с диском в его конце** (`UndiffedEdits.settle`, с тестами), а не «откат смелее»:

- **На `result` IDE держит каждый файл хода против диска** (`settle` в подписчике строк хаба, по
  `AgentStream.isTurnResult`, а не по подстроке: вывод инструмента может содержать те же слова). Ожидаемое -
  правки хода, приложенные к тому, с чего ход начал файл: к пустоте у созданного, к копии CLI у правленного (те же
  `file-history`, что у больших правок). Совпало - ничего не шлётся, так почти всегда.
- **Не совпало - панели уходит настоящий итог хода по файлу** (событие `files_settled` в ленте, прямо перед
  `result`, поэтому список ещё открыт): дифф от того, с чего ход начал, до того, что стоит на диске, и его цифры.
  `settleChanges` в `feed/changes.ts` заменяет у строки цифры и правки целиком. Откат и возврат дальше работают как
  всегда, только по правде: созданный файл удаляется, правленный встаёт как был до хода, чужая строка, добавленная
  после хода в другом месте, остаётся. Цифры тоже правдивые: строка созданного файла говорит, сколько в нём строк
  вышло, а не сколько написал Write до форматтера.
- **Созданный файл едет как «создан пустым и заполнен»** (`create` с пустым текстом и патч), а не `create` с
  текстом: текст тогда идёт короткими строками ханков, а журнал режет длинные строки (`JournalTrim`, строка длиннее
  32 КБ в записи больше 128 КБ). На живом ходе из отзыва событие весило 239 КБ.
- **Основа созданного файла - текст из вызова, как у панели** (`written`, ловится по строке ассистента с вызовом
  Write). У субагента вызова в ленте нет, и там основа - `content` результата, тоже как у панели (`changeOf`). Если
  основы разойдутся, сверка увидит расхождение там, где его нет у панели, или наоборот - и файл памяти снова не
  откатится.
- **Копия берётся та, которую CLI записал для этого хода, а не новейшая на диске** (`UndiffedEdits.Copies`, с
  тестами). CLI копирует отслеживаемые файлы на сообщение человека (переиспользуя копию, если файл с ней совпадает),
  а впервые тронутый файл - перед первой правкой, и каждый раз пишет в транскрипт, какую копию взял
  (`file-history-snapshot` и `file-history-delta`, имя копии - первые 16 hex sha256 полного пути). Ход, начатый
  уведомлением фоновой задачи, снимка не получает (по коду 2.1.293: снимок делается для сообщений без `isMeta` и без
  тегов уведомлений) - копию в нём получает только впервые тронутый файл. Новейшая копия на диске остальных тогда - файл до прошлого хода, до `sed` агента в отдельном ходе, до
  правки руками, и дифф от неё унёс бы всё это в откат этого хода, а откат, стирающий чужое, хуже отказа. Поэтому
  годится только копия, записанная после конца прошлого хода (граница - длина транскрипта на `result`, а для
  разговора, впервые услышанного здесь, - на его первой строке), и ровно та, что названа: новейшая на диске может
  быть из куска, отрезанного откатом разговора. Читаются только строки, открывающиеся как запись копии: остальной
  ход - вывод инструментов - бывает мегабайтами. Граница сдвигается на любом конце хода, не только на `result`:
  остановленный, отрезанный откатом и умерший с процессом ход тоже ничего не оставляет следующему (`turnOver` из
  `onTurnEnded` и `onFinished` хаба). Из двух записей одного файла побеждает более поздняя по своему времени, а не
  по месту в файле: форку CLI дописывает записи источника в момент старта, и они могут лечь после записи его
  первого хода. Запись о копии CLI сбрасывает на диск раз в 100 мс и результат правки ради неё не держит, поэтому
  большая правка только что взятого под учёт файла приходит раньше записи своей копии: строка остаётся без диффа,
  а файл досчитывается в конце хода по одной копии (`owed`). Нет записи - нет ни сверки, ни диффа большой правки, строка
  остаётся с точными правками CLI. Сверх того первая правка хода обязана к копии прикладываться. Нет копии, файл
  больше 8 МБ, дифф длиннее 100 тысяч строк, файл удалён - сверки нет, строка остаётся как была.
- **Телефону правки не едут, если не влезают в кадр** (`UndiffedEdits.lightened` снимает `edits` у `files_settled`),
  цифры остаются. Отката там нет.
- **Чего сверка не закрывает.** Ход без `result` (остановка, смерть процесса) не сверяется - список закрывается
  раньше, чем IDE могла бы сказать. Разговор после перезапуска IDE и реплей из истории идут по диффам из транскрипта,
  как раньше: событие сверки живёт в журнале хаба, а журнал в памяти.
- Проверено на живом ходе из отзыва: его транскрипт прогнан через `settle`, все четыре созданных файла откатываются
  удалением, цифры совпали с числом строк на диске.

## Большие правки, длинные списки, список после следующего сообщения

Нагрузочная проверка 2026-10-12 в песочнице: агент заменил `foo(` на `bar(` по всем 8000 строкам двух файлов и
создал 300 файлов. Откат всех 301 файла - 2,1 с, возврат - около секунды, страница ни разу не подвисла (пауза
не больше 47 мс, длинных задач ноль), IDE зависаний не записала. Нашлось другое.

- **Большую правку CLI присылает без диффа** (2.1.293: `replace_all` по 8000 строкам - `structuredPatch: []`),
  и такой файл пропадал из списка целиком. Дифф считает IDE (`UndiffedEdits` в `ClaudeSessionHub.onAgentLine`,
  только живые строки, до журнала): CLI держит копии файлов -
  `<дом CLI>/file-history/<разговор>/<первые 16 hex sha256 от пути>@v<N>`, на них же работает его откат кода.
  Копия, которую CLI записал в транскрипт для этого хода (см. «Копия берётся та, которую CLI записал»), - файл,
  каким ход его застал; плюс уже виденные правки этого файла в ходе (`seen`, чистится на `result`) - файл перед
  этой правкой; файл на диске - после. Хунки (`LineDiff`, с тестом «туда и обратно»)
  пишутся в событие как `structuredPatch` с `accPatch: true` и `accCounts`. Нет копии, файл больше 8 МБ, дифф
  длиннее 100 тысяч строк - событие идёт как прислал CLI.
- **«Ничего не изменилось» - только запись того же текста** (`content` равен `originalFile`). Сначала пустой дифф
  рядом с непустым `originalFile` считался таким, и это отсекало ровно большие правки: в живом потоке CLI шлёт
  рядом с ними обрезанный `originalFile`, а в транскрипте пустой. Правка (Edit) не бывает пустой вовсе.
- **Где диффа нет и посчитать нечем** (разговор из истории, копий нет), файл всё равно в списке: одиночная
  замена считается по вызову, замена всех вхождений и перезапись - знаком «±» (`FileChange.uncounted`), без
  кнопки отката.
- **Телефону дифф не едет** (`UndiffedEdits.lightened` в `RemoteAgent.fitted`): мегабайты коротких строк не
  укорачиваются обрезкой строк, и кадр выбросился бы целиком. Остаются `accCounts`, панель телефона берёт
  цифры оттуда.
- **Длинный список свёрнут**: больше 12 файлов - видно первые 10, слева в нижней строке «Show all (N)» /
  «Show fewer». На 300 файлах открытый список был 6650 пикселей.
- **Список, после которого написано сообщение, - только для чтения** (`closedChanges` в `Feed`). Кнопок нет,
  строки открывают файлы, сворачивание работает. Просьба Макса: откат файлов из-под следующего запроса оставил бы
  агента работать по коду, которого уже нет, а два живых списка один над другим читаются как два решения.
- Проверить живьём: сгенерировать файлы на тысячи строк, попросить агента заменить по ним всё через `replace_all`
  и создать два десятка файлов; в списке у больших файлов цифры и кнопка, откат возвращает файл целиком.
